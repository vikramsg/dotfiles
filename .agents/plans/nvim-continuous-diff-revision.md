# Continuous Neovim Diff Review — Revised Requirements

Based on [the original plan](nvim-continuous-diff.md), with explicit requirements for retaining Differ, restoring syntax highlighting, and verifying performance with the complete experience enabled.

## 1. Required experience and behavior

- `Space gd` opens one continuous inline diff of all changed files; scrolling crosses file boundaries naturally.
- Separate files with full-width, high-contrast header bands, bold repository-relative paths, change counts, and spacing. Keep paths readable at narrow widths; counts and staged/unstaged indicators must not obscure them.
- Keep the current file path visible in a sticky window bar. Clearly distinguish staged and unstaged sections when the same file appears twice.
- Selecting a file in Differ's sidebar jumps to its header in the continuous view.
- `[` / `]` navigate hunks across files; `[f` / `]f` jump between file sections, in both directions.
- Start with three context lines; `T` toggles compact/full context without losing the selected file, source line, or column.
- Preserve automatic comparison selection and `B` switching between `HEAD` and the `main` merge-base comparison. File listings and contents must use the same resolved comparison.
- **Syntax highlighting is required in both continuous and side-by-side views.** For languages with installed parsers, preserve Differ's source-language colors alongside diff-line and word-level highlighting. Preserve Differ's existing behavior for missing parsers; do not disable syntax because a file or changeset is large.
- Highlight each file using its own language and its actual old/new source. Deleted and added lines must receive syntax from the correct version; comments and multiline strings must retain their language context. Updating one section must not erase another file's highlighting.
- `t` opens side-by-side inspection of the current file using Differ's native inspection capabilities. Returning to continuous review restores the previous logical position. Both inspection columns identify their file and source side.
- Preserve `gf` source navigation and existing Differ editing actions. File/line mapping must remain correct for additions, deletions, renames, and partially staged files.
- Keep local line/range notes, editing, deletion, reset, outdated anchors, read-only JSON output, path copying, and restart persistence. Notes remain scoped to the correct repository, branch, comparison, and source range, and stay visible across file sections.
- Preserve GitHub PR selection, overview-to-files navigation, review start/resume, line/range comments, replies, thread navigation, viewed state, composer save/cancel, and review submission. Overlays remain visible across files and survive layout transitions.
- Reject comment selections spanning multiple files or file-header rows instead of attaching them to an incorrect file. Preserve valid source ranges within one file in either selection direction.
- Preserve hunk and whole-file staging/unstaging and confirmed/cancelled discard. After staging changes a file's section, show its actual fresh Git source and keep the acted-on hunk selected so an immediate inverse action targets that hunk.
- Refresh and source editing update only affected content or decorations where the file list is unchanged. Structural changes reuse unaffected sections and preserve logical position; removing the selected file chooses a nearby surviving section.
- Loading can continue while inspecting another file or composing a comment. Switching comparisons, refreshing, entering PR overview, or closing review must prevent older asynchronous results from replacing newer state or reviving closed views.
- Keep `g?` context-aware help and `q` returning to the editor, including from inspection. Preserve existing Differ actions unless a change is explicitly discussed and agreed.

## 2. Required implementation and verification behavior

- Apply **Tidy, First**: inspect the existing Differ view, source, syntax, navigation, and review boundaries; make small preparatory refactors that expose reusable operations before implementing multi-file behavior.
- Audit the current custom implementation against Differ. Record which responsibilities can be removed, which need a small Differ extension, and which are genuinely specific to this repository. Choose the design that retains the most native behavior with the least duplicated state and lifecycle code.
- Retain Differ's diff models, stacked/split renderers, source maps, syntax projection, sidebar, navigation, editing, patch operations, composers, PR session/sidecar, and thread rendering wherever possible. Keep repository-specific comparison policy and persistent local notes in the configuration layer.
- Implement the continuous view as an extension of Differ's existing machinery. Add section identity and row offsets where required; avoid maintaining a second Git frontend, split-window manager, staging implementation, or PR lifecycle alongside Differ's equivalents.
- Where a private or single-file-only API prevents reuse, first investigate a small change within Differ to expose that operation or make it section-aware. Record the proposed API and dependency delivery approach before proceeding. Any dependency changes must be reproducible through the repository, with an explicit revision; editing only the installed plugin is not a deliverable.
- Reuse Differ's source-based Tree-sitter highlighting. Adapt syntax collection, source-map projection, and namespace clearing so highlights can be cached and updated per file/section. Keep native syntax application for native side-by-side inspection; do not parse the mixed-language aggregate buffer as one source file.
- Keep one continuous scrolling buffer with indexed file sections. Reuse immutable per-file render and syntax results; scrolling must not perform Git reads, recompute diffs, or reparse unchanged source. Section movement should translate cached coordinates rather than rebuild the source model.
- Make Git discovery/content loading asynchronous and bound concurrency. Cache by file identity and source versions, including comparison refs and worktree/index content changes, so refresh invalidates only changed results.
- Bound main-thread model preparation, rendering, syntax projection, buffer updates, and decoration work. Yield between batches through scheduling that actually lets input and redraw run. Profile first; use worker execution only for suitable measured bottlenecks, retaining the same Differ behavior and rendering results.
- Preserve complete content, source mappings, syntax, and review interactions while optimizing. Content truncation, silent feature removal, size-based syntax disabling, or compatibility/fallback shims are not acceptable performance fixes without prior agreement.
- Establish baselines on the same machine and dependency versions: native Differ for comparable single-file operations, and the continuous implementation for changeset-wide operations. Record cold and warm behavior and enough repeated samples to expose variability rather than reporting only the best result.
- Benchmark 10- and 100-file changesets with syntax highlighting enabled and installed parsers. Include mixed-language code, one very large densely changed file, a large sparsely changed file, long lines, and multiline syntax constructs. Plain-text fixtures may supplement these cases but cannot establish syntax performance.
- Measure first usable diff content, time to correctly highlighted visible content, complete loading including syntax and decorations, peak memory, longest main-thread batch, and input-to-redraw latency. Completion must include queued work; a text-filled buffer alone is not a completed review.
- Verify that measurement code does not create the bottleneck: avoid repeatedly scanning the whole buffer, and distinguish event-loop gaps from actual input latency. Record machine load and parser/configuration details with results.
- Target **no main-thread rendering/highlighting batch over 16 ms** and **no input stall over 100 ms** during loading, scrolling, file/hunk jumps, context/layout toggles, and refresh. Record first-content and total-load timings against baselines and investigate regressions. Missed targets remain unresolved until fixed or explicitly accepted; do not attribute stalls to syntax without profiling evidence.
- Create dedicated Herdr tabs and manually exercise every user-facing workflow in section 1 in real Neovim. Verify narrow/wide headers, mixed-language highlighting, both source sides, continuous scrolling, and layout/overview round trips. Do not replace these manual checks with automated UI scripts.
- In disposable repositories, manually verify staged/unstaged duplicate paths, additions/deletions/renames, stage/refresh/inverse-action ownership, cancelled/confirmed hunk and file discard, and preservation of unrelated edits.
- Manually verify local note creation/edit/delete/reset, cross-file selection rejection, simultaneous notes, outdated anchors, JSON viewing/path copying, comparison switching, restart persistence, and commenting while other files load.
- Use a dedicated test PR for live selection, start/resume, range comments, replies, composer cancellation/saving, overview transitions, and submission; report unavailable live workflows as blocked. Confirm published file/range ownership and close the disposable PR afterward.
- Run the existing Neovim review tests against the actual checkout under review. Add focused behavioral coverage where needed for file/source ownership, syntax projection and section invalidation, incremental updates, stage/refresh targeting, and stale asynchronous results. Avoid text-presence/change-detection tests and automated replicas of manual visual checks.
- After implementation checks and tests pass, launch a background advisory reviewer focused on reuse of Differ, correctness, simplification, layer boundaries, syntax preservation, and measured performance. Assess findings rather than accepting them automatically; rerun affected checks after accepted fixes.
- Freeze this revised plan when implementation starts. Record implementation decisions, evidence, deviations, and explicit user review points in `.agents/implementation-notes/nvim-continuous-diff-revision.md`. Discuss proposed feature removals or material architecture/performance tradeoffs before implementing them.
- Complete verification and advisory review before pushing the feature branch and updating or creating the PR. Keep the PR description to short bullets describing delivered features; update it when scope changes. All changes go through a PR.
